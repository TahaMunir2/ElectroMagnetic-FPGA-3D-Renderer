# System Integration on the PYNQ-Z1: Block Design, Data Flow, and Control

*This section covers my contribution to the project: the Vivado block-design
integration and its Tcl-scripted build, the role of each hardware block and how
the blocks collaborate, the CORDIC source chain, the ping-pong double-buffer and
the producer–consumer problem it solves, the AXI link to the processor, and the
multi-lane parallelism trade-off. It closes with the two demonstrations we
delivered — a 2D moving-source visualisation and a 3D rendering with a movable
camera.*

---

## 1. System overview and how the modules connect

The platform is a PYNQ-Z1 board built around a Xilinx Zynq-7020, which contains
both a dual-core ARM processor (the *processing system*, **PS**) and FPGA fabric
(the *programmable logic*, **PL**). Our design runs a 2D electromagnetic
Finite-Difference Time-Domain (FDTD) simulation entirely in the PL, displays it on
an HDMI monitor at 640×480, and lets the operator steer it live from a Python
notebook running on the PS.

The PL is organised as a single feed-forward pipeline. Each stage produces data
for the next, and the stages are deliberately decoupled so that a slow or bursty
stage cannot corrupt a downstream one:

```
              ┌─ phase ──┐
  CORDIC IP ◄─┤ source   │      one field "frame"             one video frame
              └ adapter ─┘            │                              │
   sin/cos          │ source_q313     ▼                              ▼
       └────────────┴──► FDTD quad core ──► magnitude scan ──► ping-pong ──► bridge
                          (4 lanes)          (|E|/|S|/Ey)      double-buffer   │
                                                                              ▼
                                       HDMI ◄── rgb2dvi ◄── renderer ◄── heightmap
                                                            (2D or 3D)
```

All fields are stored in **signed Q3.13 fixed-point** (16 bits = 1 sign + 2
integer + 13 fractional; the value 1.0 is the integer 8192). Most of the pipeline
runs in one 25 MHz clock domain (the pixel clock), which keeps the design simple
and removes clock-domain-crossing hazards on the field path; the 3D renderer is
the exception and runs at 100 MHz, re-joining the pixel domain through an
asynchronous FIFO. The PS communicates with the PL purely through memory-mapped
AXI registers.

The remaining sections describe each block, what it does, and — most importantly —
how it hands off to its neighbours.

## 2. Building the design from a Tcl script

The entire hardware design is generated by a Tcl script
(`create_fdtd_render_project.tcl`) rather than assembled by hand in the Vivado
GUI. Every action a designer would normally perform with the mouse — create a
project, add an IP, draw a wire, assign an address — is a Tcl command, and the
script simply records those commands so the whole project can be rebuilt from
source. This follows AMD/Xilinx's own revision-control guidance: the binary
project (`.xpr`) and block-design (`.bd`) files are *not* committed, because they
are large auto-generated XML that cannot be diffed or merged sensibly; instead the
HDL plus the build script is the single source of truth.

The script runs in clear phases:

**Phase 1 — package the custom RTL as IPs.** Vivado's block design works with
*IP blocks*, not loose source files, so each module we wrote (the source adapter,
the FDTD core, the ping-pong controller, the BRAMs, the bridge) is first packaged
into an IP. A helper procedure spins up a throwaway project, adds the source
files, sets each file's language correctly, and runs `ipx::package_project` to emit
a self-contained IP into a local repository folder.

**Phase 2 — create the main project.** The script makes the real project, points
its IP catalogue at our packaged IPs (plus the Digilent HDMI library), selects the
PYNQ-Z1 board and the exact device part, enables the XPM libraries needed for the
asynchronous FIFO, and adds the renderer source and the pin-constraint file.

**Phase 3 — build the block design in code.** This is the bulk of the script. It
creates an empty block-design canvas, then instantiates every block and connects
them explicitly with `connect_bd_net` (for ordinary signals) and
`connect_bd_intf_net` (for bundled interfaces such as AXI). It instantiates the
processor with `apply_bd_automation`, configures the clock generator, builds the
AXI interconnect, adds the GPIO blocks, and uses small slice helpers to split
32-bit registers into the individual control fields. Finally it assigns each AXI
peripheral a fixed address.

**Phase 4 — finalise.** `validate_bd_design` checks for unconnected pins and
conflicts, `make_wrapper` generates the HDL top level around the block design, and
`generate_target` produces the synthesis products.

**Phase 5 — synthesis, implementation, bitstream (optional).** Environment
variables let the same script do different amounts of work: run it plain to build
just the project, or set `RUN_IMPL=1` to also synthesise, place-and-route, and
write the `.bit` bitstream and `.hwh` hardware-handoff file (the latter describes
the address map and is what the PYNQ Python layer reads to find each peripheral).

Two different mechanisms bring logic onto the canvas, and the distinction matters:
most blocks are **packaged IPs** (`create_bd_cell -type ip`), but the renderer is a
**module reference** (`create_bd_cell -type module -reference`), which drops a named
HDL module straight in without packaging. A module reference must present a
*Verilog* top level, which is why the SystemVerilog render core is wrapped in a
thin Verilog shell.

The pay-off of this approach is reproducibility (a clean rebuild gives an identical
bitstream), reviewability (the script *is* the architecture documentation),
maintainability across our several design variants (which share most of the script
and differ in a few lines), and headless batch builds suitable for automation. The
cost is that Vivado's command-level quirks have to be understood — for example, the
address-assignment behaviour described in Section 8.

## 3. Clocking and reset

A single mixed-mode clock manager (`clk_wiz`) derives every clock from the board's
125 MHz reference:

- **25 MHz pixel clock** — drives the whole field datapath (source, solver,
  magnitude, ping-pong, bridge) and the video timing for the 2D build;
- **125 MHz serial clock** — feeds the HDMI serialiser, which sends pixels five
  bits per pixel-clock as TMDS;
- **100 MHz core clock** — used only by the 3D renderer.

The PS supplies a separate 50 MHz clock for the AXI register bus. Each clock domain
has its own reset block (`proc_sys_reset`) that produces a clean, synchronised
reset; resets are released only after the clock manager reports "locked," so no
block starts before its clock is stable.

## 4. The CORDIC source chain

The wave is excited by a sinusoidal point source, generated by two collaborating
blocks.

**The CORDIC IP** (`cordic_0`) is a Xilinx core configured for sine-and-cosine in
a parallel, pipelined architecture. Given a phase angle on its input AXI-Stream, it
returns the sine and cosine of that angle. CORDIC ("COordinate Rotation DIgital
Computer") computes trigonometric functions using only shifts and adds, so it is
cheap in fabric and avoids storing a large sine lookup table.

**The source adapter** (`cordic_source_adapter`, our custom block) wraps the
CORDIC and turns it into a usable source generator. Its functionalities are:

- *Phase accumulation.* It keeps a running phase and advances it by a configurable
  `phase_step` once per simulation iteration, wrapping around ±π. The step size
  sets the source frequency, and therefore the wavelength (a smaller step → a
  longer wave).
- *AXI-Stream handshaking.* It drives the CORDIC's input stream and accepts the
  output stream with the proper valid/ready protocol.
- *Amplitude scaling.* It multiplies the unit-amplitude sine by a programmable
  amplitude (Q3.13) so the source strength can be set from software.
- *DC-free injection (selectable).* A plain sine deposits net energy into the grid;
  for a *moving* source this energy freezes into a static "trail," and in a driven
  region it can make the total energy grow without bound. The adapter can instead
  emit the **first difference** of the sine (the discrete time-derivative), which
  has zero average and leaves no trail. This requires the source to be sampled
  *exactly once per iteration* so the differences telescope correctly — so the
  adapter takes a one-per-iteration `sample_pulse` from the solver rather than
  free-running.

The adapter's output (`source_q313`, with a `source_valid` strobe) feeds straight
into the FDTD core.

## 5. The FDTD solver core

The solver (`fdtd_quad_core`, wrapped by `fdtd_quad_bd_adapter`) advances Maxwell's
equations in transverse-magnetic mode over a 128×128 grid, updating the three field
components `Ey`, `Ex`, and `Bz`. Each simulation iteration scans the grid cell by
cell, applying the FDTD update equations, with a perfectly-matched-layer (PML)
absorbing boundary around the edges so waves leave the grid without reflecting.

At the integration level the adapter exposes a clean interface: it takes the
source value and position, control bits (enable, free-run, display mode, field
clear, the moving-source velocity and speed throttle), and emits the per-cell field
magnitude as a stream of writes plus a `solver_done`/`mag_done` strobe and a
rolling checksum the PS can poll to confirm the solver is alive. Internally it also
contains the **magnitude scanner**, which — once a field iteration finishes —
sweeps all cells and computes a per-cell display value in one of three modes:
rectified field strength |E|, the Poynting magnitude |S|, or the raw signed `Ey`
(which gives the smooth, scientifically clear wave view). That value is what the
rest of the pipeline visualises.

The moving-source feature lives here too: a position generator advances the source
cell by a programmable velocity each iteration and bounces it off the boundary,
producing Doppler compression of the wavefronts (and, above the numerical wave
speed, a Mach-cone shock) — the basis of the 2D demo.

## 6. The ping-pong double buffer and the producer–consumer problem

This is the most important piece of integration glue, because it reconciles two
parts of the system that run at completely different and unsynchronised rates.

**The problem.** The *producer* is the solver-plus-magnitude unit. It finishes a
new field frame whenever it happens to — and that rate varies, because the operator
can throttle the simulation, and one iteration's duration depends on grid size and
lane count. The *consumer* is the renderer, which reads the field frame to draw the
screen and does so at a fixed, unstoppable 25 frames per second dictated by the
display. If the consumer were allowed to read the same memory the producer is
writing, it would catch the buffer half-updated — the top of the screen showing the
new frame and the bottom the old one — which appears as **tearing**. The naïve
alternative, making the two stages take turns on one buffer, forces them to wait
for each other and couples their timing rigidly. This is the classic
**producer–consumer** (bounded-buffer) problem: two processes sharing data at
different rates need a hand-off that lets each run freely without ever exposing a
partially written result.

**The solution: double buffering.** We use two identical magnitude memories
(`s_mag_bram_a` and `s_mag_bram_b`) and a small controller
(`s_mag_pingpong_ctrl`). At any instant one buffer is the **write** (back) buffer
and the other is the **read** (front) buffer:

- the producer's writes are routed only to the back buffer — the controller gates
  each BRAM's write-enable with a `write_sel` bit, so the front buffer is never
  disturbed;
- the consumer reads only the front buffer, selected by a `read_sel` bit the
  controller exports;
- when the producer signals `mag_done` (a complete frame has been written), the
  controller **atomically swaps** the two roles in a single clock — the just-filled
  buffer becomes the new front buffer and the stale one becomes the new back buffer
  — and pulses `frame_ready`.

Because the swap is a single-cycle flip of two select bits, the consumer always
sees a *complete, internally consistent* frame, and the two stages never stall each
other. If the producer runs faster than the display, frames are simply dropped; if
slower, the same frame is shown again. Either way the picture is always coherent.
Each BRAM is dual-ported — port A is the producer's write path, port B is the
consumer's read path — so reads and writes use physically separate ports and cannot
collide.

Because the entire field datapath shares one 25 MHz clock, the double buffer needs
no clock-domain-crossing logic — a deliberate architectural choice that made this
hand-off simple and provably safe.

## 7. The heightmap bridge

The bridge (`s_mag_to_heightmap_bridge`) sits between the ping-pong buffer and the
renderer and provides a *second* layer of decoupling. The renderer reads its
terrain from its own dedicated heightmap memories; the bridge's job is to copy each
new field frame from the front buffer into those memories, with two safeguards:

- *It writes only during vertical blanking.* The renderer issues no reads while the
  display is between frames (the vertical-blank interval), so the bridge waits for
  that window — signalled by a `vblank` line from the renderer — before copying.
  This guarantees the renderer never reads a heightmap that is mid-update, exactly
  as the ping-pong guarantees a coherent source frame. A short guard delay lets the
  render pipeline drain first.
- *It downsamples.* The field grid is 128×128 but the renderer's heightmap is
  64×64, so the bridge reads every second row and column as it copies, and it
  applies a programmable height scale so the displayed relief can be tuned live
  from software.

The bridge latches which buffer is the front buffer at the start of each copy, so a
mid-copy swap cannot pull the source out from under it. It also broadcasts its
write to all of the renderer's heightmap copies at once (one copy in the 2D build,
fifty in the 3D build).

## 8. The AXI link to the processor

Everything the operator controls travels over AXI. The PS's general-purpose AXI
master port connects to an **AXI interconnect** (`axi_interconnect`), which fans
out to several **AXI-GPIO** peripherals; each GPIO is a simple memory-mapped block
of 32-bit registers the PS can read and write from Python. We use the GPIOs rather
than custom AXI slaves because the control set is small and static, and GPIO is the
lightest way to expose it.

The register map is organised by function:

- **control** (`0x41200000`) — source amplitude and frequency, source position,
  display mode, height scale, solver enable, sample request, field clear;
- **motion** (`0x41210000`) — moving-source velocity, simulation-speed throttle,
  source-mode and source-field selectors, and (3D build) the camera-load strobe;
- **status** (`0x41220000`) — read-only: the solver checksum and a set of status
  flags (solver done, frame ready, buffer select, busy);
- **camera** (`0x41230000`–`0x41250000`, 3D build only) — twelve signed vectors
  describing the camera basis.

Because each GPIO register is 32 bits but carries several smaller fields, the block
design uses **slice** blocks (`xlslice`) to split a register into its constituent
fields (for example, amplitude in the upper 16 bits and frequency in the lower 16)
and **concat** blocks (`xlconcat`) to gather individual status bits into the
read-back word. The PS writes a packed 32-bit value; the slices route each field to
the block that consumes it.

The GPIO outputs are quasi-static control levels, and they cross from the 50 MHz
AXI clock into the 25 MHz datapath; where a *strobe* must cross (such as field
clear or camera load), it is edge-detected through a synchroniser so a single PS
write produces a single clean event in the fabric.

**An integration lesson worth recording.** Vivado's automatic address assignment
orders AXI peripherals *alphabetically*. When the three camera GPIOs were added,
their names sorted ahead of the control block, so Vivado silently moved every
existing peripheral to a new address — and the notebook's hard-coded addresses then
pointed at the wrong blocks (the call that starts the solver landed on the camera
registers, so nothing ran). The fix was to assign every peripheral an explicit,
fixed address in the script and verify the result against the generated hardware
handoff. It is a reminder that the memory map is part of the hardware–software
contract and must be pinned down, not left to defaults.

## 9. HDMI output

The renderer produces 24-bit RGB plus video timing in the pixel-clock domain. The
Digilent `rgb2dvi` IP serialises this into the four differential TMDS pairs of an
HDMI connector, using the 125 MHz serial clock to shift each colour channel out at
five times the pixel rate. Its input is fed directly from the renderer's
`vid_pData`/`vid_pVDE`/`vid_pHSync`/`vid_pVSync` outputs, and its outputs go
straight to the board's HDMI pins via the constraint file.

## 10. Multi-lane parallelism and its trade-off

To make the solver faster, the grid is partitioned into horizontal bands, or
*lanes*, that are updated in lockstep, each lane owning its own copy of the field
memories. We settled on **four lanes**.

The benefit is direct: throughput scales with lane count. Four lanes complete one
iteration in 2,048 cycles instead of 8,192 — a **4× speed-up** at the same clock,
producing an identical result. The costs are subtler and are about memory and
boundaries, not arithmetic:

- Each lane needs its own field memories and extra read ports.
- Adjacent lanes must exchange a **halo row**: the `Bz` update at the edge of one
  lane needs an `Ey` value that physically lives in the neighbouring lane, so each
  lane has dedicated ports to read its neighbour's boundary row, and carries flags
  marking whether it owns a true grid edge (so the absorbing boundary is applied
  only at the real perimeter, not at internal lane seams).
- A counter-intuitive but pleasant result: the four-lane design used *fewer* block
  RAMs than the single-lane one (108 versus 114 primitives), because splitting the
  field memory into four smaller banks packs more efficiently into the RAM
  hardware.

Eight- and sixteen-lane versions were prototyped and then removed. Beyond four
lanes the speed-up stops paying for itself — halo-exchange and read-port pressure
grow, routing congestion rises, and, decisively, the solver was already far faster
than the 25 fps display needs, so more lanes buy nothing the viewer can see. The
one visible cost of lane partitioning is faint horizontal seams at the band
boundaries, mitigated by the halo exchange and by keeping the source off a seam. A
CPU reference (using the ARM core and its NEON vector unit) was benchmarked so the
hardware speed-up is measured against software rather than merely asserted.

## 11. Clock-domain crossing summary

The design has three crossing points, each handled explicitly:

1. **AXI (50 MHz) → datapath (25 MHz):** GPIO control levels are quasi-static; the
   few control strobes use synchronised edge detection.
2. **Render core (100 MHz) → scan-out (25 MHz)** *(3D build):* pixels cross through
   an asynchronous FIFO (`xpm_fifo_async`); the heightmap is a dual-clock memory
   written at 25 MHz and read at 100 MHz.
3. **Pixel domain → TMDS serial (125 MHz):** handled internally by the `rgb2dvi`
   IP.

Keeping the entire field path (source → solver → magnitude → ping-pong → bridge) in
one 25 MHz domain was a deliberate decision: it removes CDC hazards from the part of
the system where data integrity matters most.

## 12. The two demonstrations

The same FDTD front-end drives two renderers, chosen as an explicit trade-off
between block-RAM usage and clock speed.

**2D moving-source demo.** A top-down contour heatmap maps each pixel to a grid
cell, reads a single heightmap memory, and colours it through a sixteen-band
diverging palette (blue troughs through red crests). It needs only one heightmap
memory, which freed enough block RAM to quadruple the grid to 128×128 for finer
waves. With the moving source enabled, this view shows Doppler compression of the
wavefronts and, at higher speeds, a Mach-cone shock — the clearest, most
physically legible demonstration.

**3D moving-camera demo.** The second renderer treats the field as a height map and
ray-marches a shaded, perspective 3D landscape. It is the visually striking
showpiece, but it needs about fifty heightmap copies — roughly three-quarters of
the device's block RAM. To fit them alongside the live 128×128 solver, the renderer
runs at 100 MHz and folds the four corner reads of its bilinear interpolation onto a
single memory port across four cycles, trading a higher clock for fewer memory
ports; its output re-joins the 25 MHz pixel domain through the asynchronous FIFO.
The camera basis is exposed over AXI, so the viewpoint can orbit, tilt, and zoom
live from the notebook while the simulation runs.

The two are complementary rather than redundant: the 2D path gives clarity and
finer resolution, the 3D path gives visual impact, and together they show that one
solver core can drive two very different rendering strategies selected by a
deliberate memory-versus-clock trade-off.
